# Operation Blackout

A first-person shooter that runs in the browser, built in Three.js and
TypeScript — with **no binary assets of any kind**. Every mesh, PBR texture,
sound effect and animation is generated in code at load time.

[**▶ Play in the browser**](https://kvnloo.github.io/cod/play/) ·
[**Documentation**](https://kvnloo.github.io/cod/) ·
[**Architecture**](docs/ARCHITECTURE.md)

> **Status: experiment, not a product.** This is a research artifact exploring
> how far procedural, code-authored content can go in WebGL. Subsystems are at
> very different levels of finish. See [Known limitations](#known-limitations).

---

## The constraint

There is not a single `.gltf`, `.png`, `.wav` or `.hdr` in this repository.

- **Textures** are rendered on the GPU into render targets during boot —
  albedo, roughness, normal and AO, all from shader code.
- **Meshes** are assembled from `BufferGeometry` in TypeScript.
- **Audio** is synthesised with the Web Audio API.
- **Animation** is authored as code, not baked clips.

The point is reviewability. Every visual result traces back to source you can
read and diff, rather than to a binary someone exported years ago. It also
means `git clone` is small and the whole project is inspectable in a text
editor.

## Quick start

```sh
git clone https://github.com/kvnloo/cod.git
cd cod
npm install
npm run dev        # http://127.0.0.1:5173
```

Requires **Node 20+** and a browser with **WebGL2**. A discrete GPU helps but
the `low` quality preset is intended to run on integrated graphics.

```sh
npm run build      # production bundle to dist/
npm run preview    # serve the production build
npm run typecheck  # tsc --noEmit, must be clean
```

## How it is organised

Sixteen subsystems under `src/`, each registered as a `System` in
`src/main.ts` and communicating over an event bus:

| | |
|---|---|
| `core/` | engine loop, event bus, seeded RNG, settings |
| `render/` | frame graph, post-processing stack, atmosphere |
| `material/` | procedural PBR texture generation |
| `shaders/` | GLSL, loaded via `vite-plugin-glsl` |
| `world/` | procedural level construction |
| `weapons/` | ballistics, recoil, procedural weapon meshes |
| `characters/` | procedural character geometry and animation |
| `player/` | movement state machine, camera rig |
| `physics/` | Rapier integration |
| `ai/` | enemy behaviour |
| `fx/`, `audio/`, `ui/` | pure listeners — no gameplay system knows they exist |
| `net/` | wire protocol, prediction, interpolation, lag compensation |
| `session/` | menus, lobby, matchmaking, match lifecycle |
| `game/` | game modes and rules |

Four rules matter more than the rest, and the [architecture
doc](docs/ARCHITECTURE.md) covers them properly:

1. **No binary assets.** If you need a texture, generate it.
2. **Determinism.** All randomness comes from `src/core/Rand.ts`. Never call
   `Math.random()` — the capture tooling depends on reproducible runs.
3. **Talk through the bus.** Add event names to `GameEvents` rather than
   reaching into another system's internals.
4. **Fixed step for simulation.** Physics, movement, AI and ballistics run in
   `fixedUpdate` at 120 Hz. Presentation runs in `update`/`lateUpdate`.

## Verification tooling

`tools/` holds 45 headless harnesses that drive the engine through Playwright
or Node. They are the project's test suite. The most useful:

```sh
node tools/net-protocol.mjs     # 100 assertions on the wire format
node tools/session-flow.mjs     # drives the full session journey, then
                                # re-runs it injecting failure at each stage
node tools/smoke.mjs            # gameplay smoke test
npm run shots                   # GPU screenshot capture
npm run perf                    # frame-time profiling
```

The netcode and session layers are specified as **executable contracts** — the
prose in [`docs/NETCODE.md`](docs/NETCODE.md) and
[`docs/SESSION.md`](docs/SESSION.md) is the source of truth, and those
harnesses assert the code matches it.

## How this was built

This repository was generated by Claude Code from [a single
prompt](prompt.md), fanning out parallel subagents across subsystems with
adversarial critic agents scoring output against shipped AAA titles and looping
until they passed.

That explains the shape of the docs: they are written as contracts between
independent authors who could not talk to each other. It also explains the
unevenness — some subsystems went through many critic rounds, others through
one.

## Known limitations

Being straight about this, because the screenshots flatter it:

- **Not feature-complete.** Multiplayer contracts are specified and unit-tested,
  but the stack is not proven end-to-end against real peers.
- **Spec/code drift.** [NETCODE](docs/NETCODE.md) documents its own known
  divergences in §0.1 rather than hiding them. Closing those is open work.
- **Performance varies widely** by GPU. The quality presets need tuning.
- **No automated CI for visual regressions** — capture tooling exists but is
  driven manually.
